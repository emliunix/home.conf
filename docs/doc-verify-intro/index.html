The idea

Why it exists

🧠

Before

Design rules lived in a reviewer's memory.

🔢

Version 1

A fixed list of judge questions, identified by position. Once matched 0 of 12 answers to the wrong items.

🧩

Now

The rules are a small program. Every question has a name. Every finding says why.

To read those programs you need five ideas from Datalog. Next.

Datalog · rules

A rule fills its blanks and makes a new fact

top(D, S) : core.section(D, S, _) , core.depth(D, S, 2)
: means "is true when". , means "and".
core.section(99.md, status, root)
core.depth(99.md, status, 2)
top(99.md, status) : core.section(99.md, status, root) , core.depth(99.md, status, 2) ✓ ✓
new fact  top(99.md, status)

Nothing runs in order. A rule only says when a fact is true.

Each match is a binding. The number of matches is the population. Population 0 = nothing to check.

Datalog · proofs

Every new fact remembers why

Start with a Markdown file.

Split into sections with stable ids (segments FILE prints them).

Every section, heading, depth, child and link becomes a fact.

Rules derive new facts.

Constraints say what must hold for every binding.

Some facts are questions only a model can answer. Answers are cached per section.

Each constraint ends satisfied, violated or undetermined.

One verdict and an exit code.

The machine · constraints

Anatomy of a constraint

design-verification-falsifies:
  forall:  verification_design_section(D, S)
  require: verification_falsifies(D, S)
  severity: error
  profiles: [promotion]
  message: "{S} in {D} names no observable failure witness…"
  repair:  "Name the test, command or measurement that fails…"
name shows up in every finding
forall = for every binding of this…
require = …this must hold (or forbid: must not)
error blocks · warning is reported
message + repair printed on failure, with the blanks filled
The machine · the judge

How a judge answer becomes a fact

evidence: that one section
"It works well and we are confident in it."
➜ 🤖 ➜
holds
fails
unknown
threshold (e.g. 0.8)
fails
unknown

The judge sees only the question and this one section.

It answers with a probability per label.

Top answer above the threshold → that label enters the rules.

Now imagine a less confident answer…

Below the threshold → unknown. A threshold never flips to another label. The report keeps both answered: fails (before) and label: unknown (after), so a weak answer can be told apart from no answer.

The machine · verdict

Three outcomes, one verdict

satisfied
the requirement certainly holds
violated
the case applies and the requirement can't hold
undetermined
it hangs on an unknown answer
NO-GOexit 1an error is violated
BLOCKEDexit 3a needed judge answer was never obtained
NEEDS-REVIEWexit 2an error is undetermined, or warnings too low
PASSexit 0none of the above

Checked top to bottom: the first that applies wins. With no judge key, structure is still fully checked.

Write your own · reading the proof

"Possible but absent"

  population 1 (1 certain)
    D=docs/bad.md

Read it top to bottom: one top-level section exists (scope), so the rule applies. No fact can make status_section true, so the requirement is impossible.

The one syntax trap that bites everyone: text values take single quotes. 'Status' is a word. "Status" is a list of character codes, so the rule silently matches nothing. The good page then fails with "missing … is not possible", and there is no syntax error to warn you.

Write your own · parents and children

Rules over the section tree

The tree is part of the core facts, so a rule can talk about structure directly:

FactMeaning
core.section(D, S, P)P is the parent of S (root at the top)
core.child(D, P, C)C is a direct child of P
core.descendant(D, A, X)X is anywhere under A
core.depth / core.orderheading level / position in the document

Example: every decision under ## Decisions must have a #### Why child.

  decisions(D, S): core.section(D, S, _), core.heading(D, S, 'Decisions')

constraints:
  every-decision-says-why:
    forall: decision(D, C)
    require: has_why(D, C)
    severity: error

Part 4

What trips people up

Each of these happened for real, in this repo or in visflow.

Trap 1

Nothing to check counts as a pass

In the first try at the semantic demo, the heading was ## Verification. This module looks for ## Verification design. Nothing matched, and the verdict was PASS.

constraint design-verification-falsifies [error, require]
  population 0 (0 certain)
  status satisfied

A forall with no bindings is vacuously satisfied, and the count shows only in --verbose.

When "nothing matched" is itself a defect, add population: nonempty to the constraint. An empty population then fails at the constraint's severity, and no judge question is asked.
design-verification-falsifies:
  forall: verification_design_section(D, S)
  require: verification_falsifies(D, S)
  severity: error
  population: nonempty

Traps 3 to 6

Four more first-week surprises

A new worktree says BLOCKED

The judge key comes from a gitignored .env.doc-verify symlink at the worktree root. A fresh git worktree doesn't have it, so semantic checks report TYPESAFE_API_KEY is unavailable. Fix: add the symlink.

"Run the hook" is not "check the repo"

prek run --all-files reads the index and can be green without reading any document. To check every document, run doc-verify check --all.

A code-only change is skipped

If no configured document changed, nothing is checked. That prints success too, but it is not the same as "every document passed".

Old configs are refused

A design-02 style verification: rubric is refused with a migration hint, not ignored. Examples older than design 04 will not run.

From CowBoy's notes on real incidents.

Writing modules

Modules compose by adding, never overriding

  • Reference a module as doc-verify:NAME (shipped with the engine) or as a repository path.
  • A config rule lists several modules, and the engine merges their params, oracles, rules and constraints into one program.
  • A name defined twice is refused. A child can add constraints but cannot change an inherited one, not even to make it stricter.

Design 04 describes waive: and module-level overrides. The shipped engine does not support them: a module that still carries extends or waive after composition is rejected.

## Problem statement

Design 02's rubric is a configuration schema for a fixed program. Each item is one
`choose` question over fixed evidence. Structure checks live in TypeScript, and the
Prolog is three generated clause templates. Authors therefore cannot state:
- a class of section;
- a rule over that section's children;
- a must or must-not rule per class;
- a relation between sections.

Identity is positional or built by joining strings. That caused a live binding defect
(0/12 correct) and a nested double send, which upstream patched by comparing byte
spans. Rubric libraries share one global item namespace, so they cannot be composed. A
failure reports only the first deciding clause, not why each check failed or what
would repair it.

## Scope - what we touch

- A module format (`kind: verification-module`) with imports, aliases, parameters,
  `extends`, `waive`, and qualified names.
- Segmenter facts for a section tree keyed by document, and evidence expressions over
  that tree.
- Oracles: typed judge predicates. Each ground atom is one keyed question, cached per
  atom.
- Stratified rules and constraints evaluated in Kleene three-valued logic, with rounds
  of judge requests bounded by a declared depth.
- Verdict policy written as a module over constraint results.
- Diagnostics with populations, proof trees, oracle tables, and repair hints.
- A one-shot migration of the v1 rubric schema and its nine home.conf consumers, and
  deletion of the v1 reader.

Non-goals:
- Propagating probabilities through rules.
- Recursion through oracles.
- Rules generated by the judge.
- Arbitrary Prolog: `assert`, cut, IO, or modules at run time.
- Imports across repositories.
- A full abductive search for repairs.
- Automatic calibration in CI.
- Any change to document selection (`selection.ts`), snapshots, CLI modes,
  attestation, or the outbound policy.

## Rationale

The owner's examples are quantified relations over a tree:
- a child of a section of class A has class B, C, or D;
- a section of class B does not contain X.

The smallest machine that states them is Datalog over tree facts, with some predicates
answered by the judge. Datalog has three properties this design relies on:
- **Stratification** gives negation one meaning.
- **Range restriction** keeps every rule finite.
- **A proof tree** exists for every derived fact, and that proof tree is the
  diagnostic.

Prolog is the host because DeepClause runs SWI-Prolog locally. Pure rules cost no
judge call.

Judge answers enter at the leaves as three-valued facts. Probabilistic logic
programming (distribution semantics, ProbLog) assumes independent probabilistic facts.
Answers from one judge context are correlated, as design 02 already records, and
JEV's numbers are not calibrated. Propagating them would give a precise-looking number
without meaning: twelve independent 0.9 answers multiply to 0.28 even when every child
is fine. A threshold that can only demote keeps the arithmetic out of the rules and
the provenance in the report.

Identity is the root of the reported defects. So every addressable thing has a
qualified name, and a question is identified by its ground atom, not its position.

Alternatives rejected:
- **Keeping the v1 schema and adding operators** keeps the positional and global
  identity that caused the defects.
- **A general embedded Prolog** loses the static checks that make evaluation finite
  and explainable.
- **A dual reader for v1 and v2** is a second world with nine consumers. A one-shot
  migration is cheaper.

## Assumptions and evidence

**Observed facts**

- **Binding.** Keyed evidence with named instructions fixed batch binding. Measured
  live through `evaluateSemantic` against jev-1.13.0: 0/12 correct before commit
  `d0a02a9`, 12/12 after it.
- **The threshold input.** For `choose`, JEV returns a `distribution` whose argmax is
  the chosen label. In one answer, `confidence` was 0.87 while the argmax distribution
  value was 0.91, so `confidence` is not that probability. Thresholds read the
  distribution.
- **Context through arguments.** In one live batch of 12 scope items, 8 depended on
  their parent heading.
  - With section text alone, those 8 all came back `unknown`.
  - With the parent heading supplied, all 8 were correct, and the other 4 stayed
    correct.
  - So context such as the parent heading has to reach the judge through the atom's
    arguments.
- **Local Prolog.** Pure Prolog runs locally in the DeepClause runtime (about 16 ms)
  with no judge call.
- **Schema limits in the v1 source.** `rubric.ts` allows only `question.kind: choose`
  and `evidence.source: section_body`. It rejects a duplicate item id across the whole
  inheritance chain, so two libraries that each define an item cannot be combined.
- **Nested double send.** Upstream commit `a616af3` avoids it by comparing byte spans,
  so the tree is currently reconstructed rather than modelled.
- **Nesting baseline.** At pin `c2f1560`, sandbox-deploy `c9edcf0` has 19 documents,
  298 section facts, 104 selected facts, and 0 nested pairs. A seeded case gives
  exactly 1 hit (design/103).
- **A silently narrowed item.** The v1 `goal.coverage_complete` item lists
  `user-requirements-frozen-root`, but the heading "User requirements - frozen root"
  slugs to `user-requirements---frozen-root`.
  - The item runs over `ac-coverage` alone and returns `unknown` (0.92 to 0.95) on
    goals 02 and 03.
  - An exact slug that matches nothing narrows an item without any finding. In this
    design, a selector that resolves to an empty population is printed with its count
    of zero.

**Inferences tested by implementation**

- The Prolog reader in the WebAssembly runtime can parse rule bodies with variable
  names, so no second parser is needed.
- Two-bound evaluation reproduces the v1 verdict on all nine migrated contracts.
- A labelled fixture set can calibrate each oracle's threshold. Until it runs, no
  default threshold is claimed.
- A depth-2 program costs exactly one extra judge call per run.

## Language

### Modules and references

A module is one YAML file:

```yaml
schema_version: 2
kind: verification-module
module: design-contract            # display name in diagnostics
imports:
  core: doc-verify:core            # engine library, versioned with the engine
  verdict: doc-verify:verdict/strict
  purpose: {module: ./purpose.yaml, params: {classes: [problem, scope, rationale]}}
params:
  scope_categories: [inclusion, exclusion, non_goal]
extends: [purpose]                 # inherit these imports' constraints
exports: [scope_item/3, scope-children-classified]
rounds: 2
oracles: {}
rules: {}
constraints: {}
waive: {}
```

**References.** A reference is either `doc-verify:NAME` or a repository-relative path.
- Path rules are those of design 02: no absolute paths, no repository escapes, no
  symlink escapes.
- A module instance is identified by (path, blob hash, canonical params).
- Names resolve to `instance::name/arity`, and expressions refer to them as
  `alias.name`.
- An import diamond with equal params shares one instance. An import cycle is an
  error.
- An unexported name is private.
- Two libraries that both define `problem` compose under different aliases.

**Extends.** A module inherits every constraint of the modules it `extends`. Without a
waiver, a child may make only changes that can never improve the verdict of any
document:
- add an `error` constraint;
- raise an inherited constraint's severity from `warning` to `error`;
- widen the profiles an `error` constraint runs in.

Any other change to an inherited constraint or oracle needs `waive: {qualified-name:
reason}`. That covers dropping, lowering, narrowing, adding a `warning`, widening a
`warning`, and any threshold, evidence, or label change. The reason appears in every
report.

A `warning` is not waiver-free either, because warnings share one weighted ratio.
Suppose a parent's warnings are satisfied 1 of 2 against a threshold of 0.6. A child
that adds one satisfied warning moves the ratio to 2/3 and the verdict to `PASS`.

A threshold is not a tightening. Raising one demotes more answers to unknown, which
turns a certain `forbid` violation (`NO-GO`) into `undetermined` (`NEEDS-REVIEW`).

Rules are never overridden, because names are namespaced.

**Params.** A param is substituted at instantiation time, and `$name` refers to it.

The companion `verification` block names a program and keeps design 03's profiles:

```yaml
verification:
  kind: jev-prolog
  program: ../doc-verify/contracts/design.yaml
  profiles:
    draft: {sections: [problem-statement, rationale], cache: reuse}
    promotion: {cache: refresh}
```

The companion may instead carry an inline module under `program:`, which `extends` a
shared one. A constraint can carry `profiles: [promotion]`. The default is every
profile.

### Facts and evidence

`doc-verify:core` provides these facts for each selected document `D`:
- `section(D, S, Parent)`, where top-level sections have `Parent = root`;
- `heading(D, S, Text)`, `depth(D, S, N)`, and `order(D, S, I)`;
- `meta(D, Key, Value)` from the companion's `document` block;
- `selected(D, S)` from the CLI or profile selection.

It also provides the derived relations `child/3`, `descendant/3`, and `nests/3`. `S` is
the section's slug. The tree is a fact, not a reconstruction from byte spans.

*Added 2026-10-05, because a judge cannot be trusted, and should not be paid, to notice that
a linked file is gone (visflow's constitution kept stale links that no oracle flagged):*
`ref(D, S, Target, Kind)` for every non-URL Markdown link target (`Kind = link`) and every
backtick span that looks like a repository path (`Kind = path`) in section `S`, with `Target`
as written; `resolves(D, Target)` when the target without its `#fragment` exists relative to
the document's directory or the repository root (a directory counts); and the derived
`dangling/4`, a ref without resolves. These are deterministic, so a constraint over them is
decided with no judge. `doc-verify:references` ships `references-resolve` (error, links) and
`paths-resolve` (warning, paths) over them.

Evidence expressions:
- `core.body(D, S)` is the heading plus the whole subtree;
- `core.own(D, S)` is the heading plus the text before the first child;
- `core.union(D, [S1, ...])` is the listed bodies in document order, where a section
  already inside another listed section adds nothing.

An expression that exceeds its `max_bytes` is `BLOCKED`. Evidence is never truncated.

### Oracles and thresholds

```yaml
oracles:
  purpose(D, S, P):
    choose: [problem, scope, rationale, other]
    ask: What is this section for?
    evidence: core.own(D, S)
    threshold: 0.8
  describes_mechanism(D, S):
    ask: The section describes how the solution works.
    evidence: core.body(D, S)
  scope_category(D, S, Parent, K):
    choose: [inclusion, exclusion, non_goal, other]
    ask: Classify this item listed under the heading "{Parent}".
    evidence: core.body(D, S)
```

- **Shape.** A `choose` oracle adds the label as the last argument, and its `ask` is
  the question. Its labels are the complete set the judge picks from. A certain answer
  can violate a constraint only if the set includes a label the constraint rejects.
  The example therefore lists `other`: an item outside the categories gets `other` and
  violates the constraint. An `unknown` answer only makes it undetermined. An `ask` oracle is
  a `choose` over `holds` and `fails`. The engine adds `unknown` to every question, so
  authors never list it.
- **What the judge sees.** For each atom the judge sees the question text, with the
  atom's input arguments substituted for `{Var}`, and the atom's evidence text. It
  sees nothing else.
  - Context that matters to the answer, such as a parent heading, is an input argument
    that a rule binds.
  - Everything the judge sees is part of the atom, and therefore part of its key and
    its cache entry.
- **Keys.** A ground atom is one question. Its canonical key names both its evidence
  entry and its instruction ("Judge ONLY state.evidence.KEY."), so binding holds by
  construction.
- **Cache.** The cache key is (model, question text, labels, evidence hash, policy
  version), for each atom.
- **Threshold.** Let `L` be the argmax label and `p` its distribution value.
  - If `L` is not `unknown` and `p >= threshold`, `L` is true and the other labels are
    false.
  - Otherwise every label is unknown.
  - A missing distribution is unknown and adds a finding.

  A threshold can demote an answer to unknown and never turns it into another label.
  No rule reads `p`. The report shows it, and review order uses it.

### Rule syntax

Rules are YAML keys with term bodies:

```yaml
rules:
  scope_item(D, P, C): core.section(D, P, _), purpose(D, P, scope), core.child(D, P, C)
  scope_class(D, C, K): scope_item(D, P, C), core.heading(D, P, H), scope_category(D, C, H, K)
```

Constraints use YAML forms:

```yaml
constraints:
  scope-children-classified:
    forall: scope_item(D, P, C)
    require: scope_class(D, C, K), K in $scope_categories
    severity: error
    message: "{C} under {P} is none of {scope_categories}"
    repair: "Rewrite {C} as one of {scope_categories}, or move it out of {P}."
  problem-states-no-mechanism:
    forall: core.section(D, S, _), purpose(D, S, problem)
    forbid: describes_mechanism(D, S)
    severity: warning
    weight: 1
```

The body grammar is:
- a conjunction with `,`;
- `not G`;
- `X in List`;
- comparisons between integers;
- `count(V, G, N)`, a stratified aggregate.

The runtime's Prolog reader parses each body. The checker then rejects:
- a predicate that is neither declared, imported, nor a built-in;
- an unsafe variable (range restriction);
- negation or `count` over a predicate in the same or a higher stratum;
- an oracle inside a recursive cycle;
- an oracle whose arguments are not bound by earlier positive literals;
- an oracle depth above `rounds`.

Rules may recurse, which `descendant/3` needs.

## Evaluation

Each predicate is evaluated to two bounds:
- the **certain** bound treats unknown oracle atoms as false;
- the **possible** bound treats them as true.

`not G` reads the possible bound of `G` when it builds the certain bound, and the other
way round. Stratification makes this well defined. An atom is:
- true if it is certain;
- false if it is not even possible;
- unknown otherwise.

That is Kleene's strong three-valued logic.

Each stratum is computed bottom-up to a fixpoint, the certain bound first and then the
possible bound. Rules are range-restricted over finite facts, so each fixpoint is
finite.

`count(V, G, N)` yields the interval [certain count, possible count]. A comparison is
certain if it holds over the whole interval, and possible if it holds for some value in
it.

A constraint is judged for each binding of `forall`:
- **violated** when the binding is certain and the goal is not possible;
- **satisfied** when the goal is certain;
- **undetermined** otherwise.

`forbid: G` means `require: not G`. The constraint's result is violated if any binding
is violated, else undetermined if any binding is undetermined, else satisfied.

An oracle's inputs are every argument except the label of a `choose` oracle. Rounds
work like this:
1. Round `k` asks every oracle atom that meets three conditions:
   - its inputs are bound;
   - every oracle literal before it in its rule or constraint instance is already
     answered;
   - the instance is still possible.

   Literals are read left to right, as Prolog reads them. So the author's order
   decides what is asked, and nothing is asked for an instance that an earlier answer
   has already ruled out.
2. Answers become facts, and the bounds are recomputed.
3. An atom that is never asked belongs to no possible rule instance, so no result
   depends on it.

An oracle's depth is the longest chain of oracle literals that reaches it, read left
to right through rules. The checker's depth bound guarantees that no possible atom is
left unasked after `rounds` rounds. The example has depth 2, because `scope_category` is asked only about
children of sections that could be classified as `scope`.

**Judge requests.** One artifact makes at most `rounds` judge requests. The default is
1. Each request is one keyed batch, and each one separately has:
- a capability check;
- an outbound-policy check;
- a byte budget.

An over-budget batch is `BLOCKED` and is never split. A round with no atoms to ask makes
no request. The attestation records each request's identity in order. A depth-1 program
keeps design 02's one-request boundary.

The verdict is a module over `result(Constraint, Status, Severity, Weight)` facts.
`doc-verify:verdict/strict` carries design 02's outcome table:
- an `error` constraint that is violated gives `NO-GO`;
- an `error` constraint that is undetermined gives `NEEDS-REVIEW`;
- `warning` constraints give the weighted ratio of satisfied weight to total weight,
  and a ratio below the threshold gives `NEEDS-REVIEW`;
- an engine failure gives `BLOCKED`.

Precedence stays `NO-GO`, `BLOCKED`, `NEEDS-REVIEW`, `PASS`.

## Diagnostics

For each constraint the report gives:
- **Population:** the `forall` bindings, printed before any judgment, with a count.
- **Status:** satisfied, violated, or undetermined.
- **Each failing binding:**
  - its variable bindings;
  - the rendered message;
  - the repair hint;
  - the proof tree down to facts.

  A leaf that is an oracle shows its key, evidence sections and bytes, label,
  distribution, threshold, round, and cache hit.
- **Missing literals:** for a violated `require`, the goal literals that were not
  possible. For example: "no category for s-14 is certain". This is a bounded form of
  abduction. It does not search for alternative repairs.

The report also lists every oracle question asked, every waiver with its reason, and
the module instance chain with blob hashes. The text and JSON formats carry the same
fields.

## Migration

Each v1 item becomes one oracle and one constraint:
- `scope: each` becomes an `ask` oracle over `core.body(D, S)`, used in a constraint
  that ranges over the listed ids.
- `scope: combined` becomes an `ask` oracle over `core.union`.
- `@selected` becomes `selected(D, S)`.
- `critical: true` becomes `severity: error`.
- A noncritical item becomes `severity: warning` with its weight.
- A required section becomes a constraint over `heading` or `section` facts.

- A migrated oracle has `threshold: 0`, so the argmax label stands as it does in v1.
  Calibration sets a real threshold later, which counts as a threshold change and
  needs a `waive:` in a consumer that extends it.
- A section id that matches no section in the document is printed with a count of
  zero. The atom's evidence is then incomplete, so it is unknown and is not asked. v1
  narrowed silently here, and the migration gives the same verdict: `NEEDS-REVIEW` for
  a critical item.

v1 score mappings other than `{supported: 1, refuted: 0, unknown: 0}` are reported
when the migration runs and are decided case by case.

Parity has one named exception. The goal contract selects
`user-requirements---frozen-root`, the slug the heading actually has. So
`goal.coverage_complete` judges the requirements it covers, and its verdict may move
from v1's `NEEDS-REVIEW`.

The nine home.conf consumers migrate in the same change that deletes the v1 reader.
The sandbox-deploy consumers stay on pin `c2f1560` until they re-pin, and that
migration is their own change.

## Relation to designs 02 and 03

This design replaces three sections of design 02:
- "Rubric library and reference resolution";
- "Structural and semantic facts";
- "Rules and verdicts".

It also replaces design 03's clause that TypeScript owns the deterministic verdict
rules. It replaces design 02's "One request contains all questions" and design 03's
"multiple JEV calls" witness with the per-artifact bound of `rounds` requests. It is a rule language, not the workflow language that design 03 excluded:
modules cannot run commands or choose pipeline stages. Everything else in both designs
stays as it is. That covers snapshots, the affected closure, segmentation, the
outbound policy, attestation, the Prek path, and CLI modes. When this design lands,
designs 02 and 03 gain `Superseded by:` lines for those sections.

## Verification design

| Property | Failure witness | Command |
| --- | --- | --- |
| Binding by construction | Two atoms of one oracle over different sections receive each other's answer, or reordering the atoms changes any fact | `npm test -- oracles` |
| Threshold only demotes | An answer below its threshold becomes the opposite label, or any rule reads a probability | `npm test -- oracles` |
| Three-valued soundness | `forbid` or `require` over an unknown atom is `satisfied`, or `not` of an unknown atom is true | `npm test -- evaluate` |
| Static checks | An unsafe variable, a negation cycle, recursion through an oracle, a non-ground oracle call, a predicate outside the whitelist, or an oracle deeper than `rounds` is accepted | `npm test -- language` |
| Modules compose | Two libraries defining `problem` collide, a param change has no effect, a diamond creates two instances, an import cycle or repository escape resolves, or weakening without `waive` is accepted | `npm test -- modules` |
| Rounds bounded | A depth-2 program makes a number of calls other than 2, a depth-1 program makes more than 1, or an over-budget round is split | `npm test -- evaluate` |
| Extends law | A child that raises an inherited threshold, changes an inherited oracle, or adds or widens a `warning` loads without `waive:`, or any waiver-free change improves a seeded document's verdict | `npm test -- modules` |
| Diagnostics complete | A violation report lacks bindings, the population, a proof leaf with label and distribution, or the repair hint | `npm test -- diagnostics` |
| Nesting baseline | Against sandbox-deploy `c9edcf0` the populations are not 19 documents, 298 section facts, 104 selected facts, and 0 nested pairs, or the seeded case does not give exactly 1 | `node doc-verify/dist/cli.js check --paths 'design/*.md' --verbose --format json` run from a sandbox-deploy worktree at `c9edcf0` |
| R2 and R3 live | The fixture with a `scope` parent and a misclassified child does not give exactly one violation naming both sections | `DOC_VERIFY_LIVE=1 npm test -- live`, gated like `doc-verify/tests/remote-hook.sh` |
| Migration parity | A migrated home.conf contract's verdict differs from its v1 verdict at the parent commit, uncached and live, except for the named exception | `check --paths` over the nine consumers' documents with `--profile promotion --refresh`, run at the parent and at the change |
| Each migrated constraint separates | For some migrated constraint, a known-good document and a known-bad document land on the same side (both pass or both fail), uncached and live | `DOC_VERIFY_LIVE=1 npm test -- separation`, one committed good/bad pair per constraint |
| Trust boundary holds | An LLM fallback, a split batch, more requests than `rounds`, unsafe outbound evidence, or a PASS driven by confidence becomes reachable | `npm test -- semantic confidentiality` |

The deterministic gate is `npm test && npm run typecheck && npm run lint`. Each gate
listed here must first be observed failing on a seeded defect. This prevents a repeat
of the design 02 C10 miss, where the binding boundary was claimed but never observed.
